## SQLite (`helpers/db.js`)

Tables: `logs`, `held_files`, `rollback_reasons`, `custom_order_history`, `reason_definitions`, `fabrics`, `shop_profile`, `file_stages`, `file_stage_history`, `reprint_requests`, `rip_errors`, `etsy_imports`, `etsy_fabric_map`

> **Retired tables, dropped at every start (ETAP 4, 4-drop):** `initDb` runs `DROP TABLE IF EXISTS` for `RETIRED_TABLES` (`db.js`) - `counters`, `custom_clients`, `custom_order_files` (orphans of ONE development run of the abandoned `feature/custom-orders-unification` against the shared DB, never read or written by `main`) and `fabric_globals` (the class numbers' old home - see below). Each DROP on its own try/catch; a failed one is logged and retried at the next start. Row counts were measured on Alex's DB first (2026-09-28: 1 / 1 / 11 / 6, profile v3) and exported to JSON next to a copy of the file; dropped only after every station ran 1.0.27 (FILIP 2026-09-29). Do not reuse the names.

- `rollback_reasons.file_id = null` → whole batch reason; `= filename-without-ext` → single file
- `logs.workstation` can be NULL in old records — render conditionally
- `held_files` is keyed by `file_id` (PRIMARY KEY) with an optional `reason` — a **global** hold model (one operator holds a file, everyone sees it; legacy per-workstation rows are migrated to this shape on `initDb`). `file_id` == the inbox item id `${folder}_${filename.pdf}` (same key `readFolders` builds). Rows are **orphan-pruned** on a clean inbox scan (see `pruneOrphanHeldFiles`), because nothing else clears a hold when its file leaves the inbox — `unholdFile` is only ever called by the explicit in-app un-hold toggle (NOT by `createBatch`/rollback)
- Indexes: `rollback_reasons(batch_path)`, `rollback_reasons(file_id)`, `logs(timestamp DESC)`
- `getAllLogs` is capped at 500 rows; `addLog` in store trims to 500 entries
- `fabric_globals`: **dropped in ETAP 4 (4-drop), no longer created.** The class numbers belong to `profile.materialClasses` (`shop-profile.md`); the last writer went in 1.0.26. `getFabricGlobalsRaw()` stays for the profile migration v2 -> v3 (it must never write a default into the shared profile, ETAP 2g-3a): with the table gone it answers `null` without an error line, so a v1/v2 row - none exists, the live row is v3+ - stays "blocked" at v2 (S2 2026-09-28). An older build started against the DB recreates an EMPTY `fabric_globals` - harmless, the next start of a current build drops it again. `fabrics` seeding is guarded on `DEFAULT_FABRICS` being non-empty, and it ships empty — a fresh install starts with no materials (Settings > Fabrics; the shop profile import of ETAP 3 does NOT fill the catalogue)
- `fabrics` has an `alias` column (TEXT, nullable) — short path-safe name for the PRINTED folder / XML; empty/NULL alias = full `name` is used
- `fabrics.preferred_printer` (TEXT, nullable; added at start by `ensureFabricPreferredPrinterColumn`) — a `printers[].code` of the shop profile, of the fabric's OWN class (`fabricSaveError` refuses anything else; the code is compared ignoring case, like `getPrinterByCode`, and `fabrics:save` / `fabrics:setAll` STORE it as the profile spells it - `withProfilePrinterCode`, D7). `fabrics:save` also refuses a write onto a name that is not the row's own - an ADD (no `oldName`) or a RENAME in an edit (`oldName !== fabric.name`) - when that name already has a row, `fabricAddError` (D9, D20; `saveFabric` is DELETE + INSERT OR REPLACE, so it would overwrite the other material); an edit that keeps its name is not checked. A suggestion only: Print pre-selects it, nothing routes by it, the XML never sees it. A write that does not SEND `preferredPrinter` keeps the stored value (`preferredPrinterToStore`: undefined = keep, null/"" = clear) - in `saveFabric` (read before a rename's delete) and `setAllFabrics` (by name, read before the DELETE). A station on an older build rewrites the row without the column and clears it: roll out everywhere before setting preferences. **Missing column (D8):** when the start's ALTER failed (SQLITE_BUSY past `busy_timeout`), `getAllFabrics` reads `NULL AS preferredPrinter` instead of losing the whole catalogue (= every job refused until a restart); `saveFabric` / `setAllFabrics` write without the column when no row sets a preference and return `false` for one that does. `fabrics:save` / `fabrics:setAll` refuse that write first, with a readable reason (`preferredPrinterColumnError`, `fabricInput.js`), asking `ensureFabricPreferredPrinter()` - which retries the ALTER - only when a row sets a preference. Whether the column exists is a flag that each open's ensure resets and sets; while it is false every fabrics call re-reads `PRAGMA table_info`, so a column another station's start added is used at once.
- `fabric_length_extra` (`name` PK, `percent` REAL; created at start, FILIP 2026-10-20): the length allowance of a fabric - the percent its files are PRINTED longer (XML `<Height>`; the metres follow - `print-xml.md`; fabric that shrinks in the heat press). A TABLE, not a `fabrics` column, on purpose: an older build rewrites `fabrics` rows (INSERT OR REPLACE) and would clear a column it does not know; this table it never touches. One row per fabric with an allowance > 0 (0 = no row). `getAllFabrics` adds `lengthExtraPercent` (0 default) to every row; an unreadable table gives 0 and never costs the catalogue. Written by `setFabricLengthExtra(oldName, name, percent)` (after `saveFabric`; undefined = keep, follows a rename), `deleteFabricLengthExtra`, `setAllFabricLengthExtras` (setAll: a row that sends none keeps its name's, a name that left loses it) - validation in `fabricInput.js` (`isLengthExtraInput`, 0..100). The handlers report "saved, but the allowance could not be" when the second write fails (two statements, not one transaction). **Orphan rows (D72):** an older build deletes or renames a material without touching this table, so `initDb` deletes the rows whose name is not in `fabrics` - skipped while `fabrics` is empty, own try/catch - and `setFabricLengthExtra` with no `oldName` (an ADD) starts from 0, never from a row under that name.
- `reason_definitions` is populated via one-time migration from electron-store on first run
- `rip_errors`: one row per ERRORED FILE (not per xml). `UNIQUE(job_guid, file_id)` — dedup is per (xml, file); a pre-split failure shares one `job_guid` across N files → N rows. Index: `rip_errors(file_id)`. `scope` (TEXT, nullable; added at start by `ensureRipErrorScopeColumn`, 2026-10-14): `RIP_ERROR_SCOPE.FILE` / `BATCH`; NULL (older rows, older builds) = file. If the start's ALTER fails, the insert is prepared WITHOUT the column (`ripErrorsHaveScope`): rows still reach the file badges, only the batch-header badge waits for a later start.

**DB functions:** see `db.js` — exported functions check `if (!db)` and degrade (writes go through `runWrite`, which returns `false`); the deliberate exception is `getShopProfile`, which THROWS without a handle (see `.claude/rules/shop-profile.md`). Two more with a contract worth knowing: `pruneOrphanHeldFiles(liveIds)` refuses a non-array or EMPTY `liveIds`, so a failed scan can never wipe `held_files`; `resolveRipErrorsByFile(fileId)` resolves ALL open rows for that file and returns `false` instead of throwing; `resolveRipErrorsByJob(jobGuid)` the same for every row of one job (a whole-batch failure); `ripErrorJobHasOtherFiles(jobGuid, fileIds)` answers whether a job already has rows for files outside `fileIds` (the scan skips such an xml; `true` on a failed read).

**`etsy_imports` / `etsy_fabric_map`** (E3b-2, shared DB, created by `ensureEtsyTables` in its OWN try/catch - a failure costs the Etsy import, never the database; older builds never read either table, so a rollback is safe; every accessor answers "could not" - `undefined` / `null` / `false` - while `etsyTablesReady` is false). `etsy_imports`: one row per Etsy order LINE, `UNIQUE(receipt_id, transaction_id)`, `state` = `ETSY_IMPORT_STATE` (`pending` / `done` / `needs_review` / `failed`, `src/shared/constants.js`), `file_name` + `folder` (the target, written at the CLAIM so a later start can find the file), `reason` (what a person reads for `needs_review` / `failed`). `claimEtsyImport` is `INSERT OR IGNORE`: `true` = this caller owns the line, `false` = a row exists (another tick or station), `null` = the write failed - the import then does NOTHING for the line. `getEtsyImport` tells "never seen" (`null`) from "could not ask" (`undefined`) - never collapse the two. `etsy_fabric_map` (`etsy_key` PK = `etsyKey(etsy_name)`, `fabric_name`): Etsy's name of a fabric -> a `fabrics` row (shared config, rule 16; edited in E4). Seeded with the seven non-spelling pairs (`ETSY_FABRIC_SEED`) ONLY by the start that creates the table (`sqlite_master` is asked BEFORE the CREATE), and only pairs whose `fabric_name` is in `fabrics` to the character - another shop's DB gets no row, and a deleted pair never returns. No Etsy credential is ever in these tables (rule 25; `etsy.json`).

**`etsy_imports`, the E4 half (Inbox bar, plan E4a).** Four nullable columns, in the CREATE and added by `ensureEtsyImportDetailColumns` (ALTER) to a table an E3b-2 build made: `title`, `quantity`, `listing_id` (what the bar shows - written ONLY by the importer, the one station signed in to Etsy, at every claim and every move of a RETRY; no backfill) and `manual_xwd` (the number a person typed in). A failed ALTER (`etsyImportsHaveDetails` false) costs the bar only: claim / get / setState / move work as before without the columns, and `listOpenEtsyImports` / `requestEtsyImportRetry` / `dismissEtsyImport` answer `null` ("could not"), never an empty list. Two more states: `retry` (a person's request from the bar of ANY station; only the importer acts on it) and `dismissed` (not a print, never imported). The bar's list = `ETSY_IMPORT_OPEN_STATES` (needs_review, failed, retry). The two requests are GUARDED UPDATEs and return `{ updated }`: Retry from needs_review / failed only, Dismiss from needs_review / failed / retry - a RETRY waits for the importer, and with the importer off it would stay in the bar for good (an order the tick does not list is fetched by number and a refused one goes back to needs_review with Etsy's answer - `listEtsyImportRetries`, `retryUnlisted`); racing the importer is safe, its CAS from RETRY then matches no row. A done, pending or dismissed line is never reopened from the bar. `moveEtsyImport({ from: [...] })` is the importer's CAS (RETRY -> PENDING / NEEDS_REVIEW); it refuses an empty `from` (`null`), so there is no unguarded UPDATE through it. The number is six digits (`ETSY_XWD_INPUT_RE`), checked in the IPC (`helpers/etsyImportRequests.js`) AND in the engine.

**`etsy_imports.suggested_xwd`, the E4c half** (TEXT, nullable; in the CREATE and added by `ensureEtsyImportSuggestionColumn` with a flag of its OWN, `etsyImportsHaveSuggestion` - a failed ALTER costs the suggestion only, the bar and the import keep working and the column reads as `NULL AS suggestedXwd`). The number the importer found in the library for a line that stopped at the XWD number (none on the line, or no image for it): `helpers/etsySuggestion.js` `suggestXwdForTitle` - the library design must OPEN the listing title as whole words and the designer must stand in it, exactly ONE number may match and it must have exactly one image. Written ONLY by the importer, at the claim and by `moveEtsyImport` (`details.suggestedXwd`: undefined = say nothing, null = clear, six digits = store; anything else is NULL). A hint for the bar, NEVER used to name or copy a file: the copy still needs a number from the line or one typed in. An unreadable library or no single match costs the hint, not the line. No backfill - a row written before E4c has none until a Retry stops again.

**`etsy_imports.ship_by`, plan ETA** (INTEGER, nullable, epoch SECONDS; in the CREATE and added by `ensureEtsyImportShipByColumn` with a flag of its OWN, `etsyImportsHaveShipBy` - a failed ALTER costs the date only). Etsy's `transactions[].expected_ship_date` of the line, from the receipt the importer already fetches. A valid value is `etsyShipByOf` (`src/shared/etsyShipBy.js`, both processes): a safe integer above 0 and below `ETSY_SHIP_BY_MAX` (1e11 - a millisecond value is refused); anything else is "Etsy said nothing usable". Written ONLY by the importer: at the claim (`details.shipBy`, invalid = NULL), by `moveEtsyImport` (a valid `details.shipBy` only - the move never clears it) and by `setEtsyImportShipBy({ receiptId, transactionId, shipBy })`, the refresh of a line that already has a row in ANY state but RETRY (whose move carries it): `UPDATE ... SET ship_by = ? WHERE ... AND ship_by IS NOT ?` -> `true` written / `false` no row or the same date / `null` no column, invalid value or failed write. It does NOT touch `updated_at` (that orders the bar and ages a PENDING row). The importer compares in memory first, so an unchanged date costs no write on the share; a failed write is logged and the line goes on (`refreshShipBy` in `helpers/etsyImport.js`). `getEtsyImport` returns `shipBy` ONLY when the column exists (no key = nowhere to keep it; `null` = no date yet). The dry run (Check newest order) shows the date and writes nothing. Read for the "Ship by" badge (ETA-2) by `listEtsyShipDates(receiptIds)`: ONE `SELECT receipt_id, MIN(ship_by) ... WHERE state != 'dismissed' AND ship_by IS NOT NULL AND receipt_id IN (...) GROUP BY receipt_id` -> `{ receiptId: epoch s }` with only the orders that have a date (a "not a print" line is not part of what has to leave); `null` = could not ask (no column, no table, a failed SELECT) - never `{}` for that, `{}` means "asked, no dates". The IPC caps the list at `ETSY_SHIP_DATES_MAX` and drops any value `etsyShipByOf` refuses. SQL proven on the real driver: the writes in `agents/chat/artefakty/eta-1/sql-proof.cjs`, this read in `agents/chat/artefakty/eta-2/sql-proof.cjs`. **MSG-2 changed that read:** `listEtsyShipDates` now answers `{ receiptId: { shipBy, buyerNote } }` (each a value or `null`; an order with neither is not a key) from ONE statement - `MIN(ship_by) AS shipBy`, `MAX(buyer_note) AS buyerNote` (the note is the receipt's and sits on every line; should lines differ for a moment the greatest wins), `WHERE state != 'dismissed' AND receipt_id IN (...) GROUP BY receipt_id HAVING shipBy IS NOT NULL OR buyerNote IS NOT NULL` - the old `ship_by IS NOT NULL` filter is gone because it would hide an order that has a note and no date. `null` still means "could not ask", gated by `etsyImportsHaveShipBy` as before; without the `buyer_note` column the note half is `NULL` (dates only). The IPC cleans both halves again. SQL proven on the real driver: `agents/chat/artefakty/msg-2/sql-proof.cjs`.

**`etsy_imports.buyer_note`, plan MSG** (TEXT, nullable; in the CREATE and added by `ensureEtsyImportBuyerNoteColumn` with a flag of its OWN, `etsyImportsHaveBuyerNote` - a failed ALTER costs the note only). The order's `message_from_buyer` (the RECEIPT's free text, from the receipt the importer already fetches), kept on EVERY line of the order like `ship_by` - no table of its own. A usable value is `etsyBuyerNoteOf` (`src/shared/etsyBuyerNote.js`, both processes): a string; CRLF / CR -> a newline, a tab -> a space, every other control character (C0, DEL, C1) and the bidi embedding / override / isolate marks dropped; trimmed; cut to `ETSY_BUYER_NOTE_MAX` (2000) code points without splitting a character; empty = `null` ("Etsy said nothing usable"). HTML entities are kept as Etsy sends them until a live Check newest order shows them. Written ONLY by the importer, by the same three paths and rules as `ship_by`: the claim (`details.buyerNote`, refused = NULL), `moveEtsyImport` (a usable note only - never cleared) and `setEtsyImportBuyerNote({ receiptId, transactionId, buyerNote })` (`... AND buyer_note IS NOT ?`, `updated_at` untouched; `true` / `false` / `null` as `setEtsyImportShipBy`), compared in memory first (`refreshBuyerNote`). `getEtsyImport` returns `buyerNote` ONLY when the column exists. A CUSTOMER's words: never in the log, a notification, a file name or an error - a failed write logs only the error's code / kind, never its message (which could quote the value). The dry run answers it as `buyerNote` NEXT TO `receipt` (`receiptFacts` carries no buyer data) and writes nothing; Settings shows it as React text. Read for the bubble beside "Ship by" (MSG-2) by the SAME `listEtsyShipDates` as the date (below). SQL proven on the real driver: `agents/chat/artefakty/msg-1/sql-proof.cjs`.

**`file_stages.ext`** (TEXT, nullable; added at start by `ensureFileStageExtColumn`, E3a-2): the extension of the tracked file, so Production builds `<file_id>.<ext>` and not a hard-coded `.pdf`. **NULL = pdf** — every PDF row, and every row an older build wrote. Written ONLY by `submitBatch` (`insertFileStage`), and only for an IMAGE (`stageExtToStore` stores NULL for a PDF), spelled as the file is on the disk. Read ONLY through `stageFileExt` / `stageFileName` / `stageFilePath` (`src/shared/artworkFile.js`): a value outside `IMAGE_EXTS` (compared without case) reads as pdf, so a database value never reaches a path raw. Never write `${file_id}.pdf` in the UI (Production, SewingReceive, orderSearch all go through the helper). If the start's ALTER fails (SQLITE_BUSY), the INSERT is prepared without the column: a PDF row still registers, an IMAGE row makes `insertFileStage` return `false` (submitBatch's tracking warning) — pinned by `db.fileStageExt.test.js`.

**`reprint_requests`** (partial reprint tracking): one row per rollback-from-Production event. `qty_affected` REAL — meters for LM, piece count otherwise; `qty_original` = full qty at rollback time. Open = `fulfilled_at IS NULL AND superseded_at IS NULL`. A new rollback of the same file **supersedes** prior open rows (history kept for analytics). `stage:advance` to `packed` **or `shipped`** calls `fulfillReprintRequests(fileId)` (the shipped case is Mark as Shipped jumping past packed, 25d1a4d). Index: `reprint_requests(file_id)`. When a Production rollback registers a qty, `rollback_reasons.meters` is estimated from **qty_affected** (LM: meters→height; others: pieces→qty), so Analytics waste (byFabric, Details) is partial-aware with no Analytics-side changes; BatchHistory rollbacks keep full-file meters. `readFolders` attaches `reprintQty`/`reprintQtyOriginal` to inbox file objects from open requests (matched by filename stem); `readSingleBatch` (BatchHistory) **prefers the persisted provenance in `_batch_info`** for reprint, falling back to open requests only when `_batch_info` has none → persistent blue "Reprint" badge in DataList and BatchHistory `FileRow`. **`selectedOverrides` holds ONLY manual operator overrides — never seed it from reprint.** At submit, `fileService.submitBatch` computes `effectiveQty = manualOverride ?? reprintQty ?? parsed`, and only the effective amount drives the printed output (XML `<Copies>`/`<Height>`) and the `_batch_info.json` provenance — `createXML.js` still needs no reprint logic. The Override and Reprint badges are independent and may coexist (Override from `selectedOverrides`, Reprint from open requests / `_batch_info`); never hide the Override badge because it equals `reprintQty`. **Reprints counter (print-view OverviewPanel):** the "Reprints" pill shows `store.openReprints.length`, loaded via `reprint:getOpen` (= `getOpenReprintRequests`, ALL open rows regardless of location) and refreshed on the global 30s poll. It counts every open request — inbox (rolled back, awaiting reprint) **+** in-production (`file_stages`) **+** any **phantom** whose file has left both (no inbox PDF and no `file_stages` row, e.g. a reprint never re-run). A phantom is invisible in every view but still counted, so the pill can legitimately read one higher than the sum of what any single view shows — the count is authoritative against the DB, not a per-view total.

**`rip_errors`** (RIP-error tracking): one row per **errored file**. Columns: `id` TEXT PK (`crypto.randomUUID`), `job_guid` TEXT NOT NULL, `file_id` TEXT NOT NULL (filename stem, matches `file_stages.file_id`), `batch_id`, `nesting_group`, `failed_node`, `error_message`, `document_id` (XWD, nullable backup key), `detected_at` (ISO ingest time), `created_at` (`<Created>` from xml, nullable), `resolved_at` (NULL = open; set by `resolveRipErrorsByFile` on TWO paths — automatically on a successful rollback, and manually from the `RipErrorPopover` "Resolved" button via `rip-errors:resolve`; see `.claude/rules/rip-errors.md`). `UNIQUE(job_guid, file_id)` + `INSERT OR IGNORE` → a pre-split failure shares one `job_guid` across N files (N rows), and re-scans don't duplicate. The **same `file_id` may hold multiple open errors** (different `job_guid` = distinct events); `getOpenRipErrors` orders `detected_at DESC` and the store keeps only the most recent per file. See `.claude/rules/rip-errors.md`.
