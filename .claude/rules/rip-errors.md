## RIP Errors

Surfaces PrintFactory job failures on the affected files. PrintFactory drops a per-failed-job pair into `{storagePath}\<folders.ripError>\` (Alex: `AUTOMATION_WORKFLOW_ERROR`): `<name>.tif` (ignored) + `<name>.xml` (parsed). Because the workflow has a Split node (`SplitOn=Document`), each failed document gets its own xml with its own `<JobGUID>`. New dependency: **fast-xml-parser** (main process only). The folder name is **shop-profile data** since ETAP 2d-3: `folders.ripError` (Alex: `AUTOMATION_WORKFLOW_ERROR`), read through `getFolder("ripError")` (`shopProfile.js`, validated by `isFolderName`). `RIP_ERROR_FOLDER` and `getRipErrorRootPath()` no longer exist. It is resolved in `ripErrorHandlers.js`, NOT in `getRootPath.js`: `db.js` imports `getRootPath.js`, so `getRootPath.js` importing `shopProfile.js` would be a cycle.

**Parser (`parseRipErrorXml.js`)** — `fast-xml-parser` (`attributeNamePrefix:"@_"`, `ignoreAttributes:false`, entity-decoding on). Returns an **ARRAY** of error rows; never throws (missing → null, malformed/non-error → `[]`, logged).

- **Detection:** any node `WorkflowResult="Fail"` OR `Job.WFState` has `@_Error`; else `[]`.
- **errorMessage** = `WFState@Error` (fallback: the Journal entry carrying `@_Error`). **failedNode** = that Journal entry's `@_Process` (pre-split → `"Hotfolder"`).
- **Scope — one file or the whole batch (2026-10-14, FILIP: "a file when one file failed, the batch when the whole batch did").** Decided by the NUMBER of `<Document>` entries in the job-level `<Documents>` (`parsed.Job.Documents`, distinct from the RipFlowJob one). Every row carries `scope` (`RIP_ERROR_SCOPE`, `src/shared/constants.js`):
  - **ONE** (failure AFTER the Split node, common) → **one** row, `scope: FILE`; the file = that document's own `Name`, falling back to the job-level `<Name>` (the document first: a one-file batch failing pre-split has the BATCH's name as job `<Name>`). Real: "Layout does not fit on any mediasize", Journal with a `Split` entry.
  - **SEVERAL** (failure BEFORE the split) → one row per batch document, `scope: BATCH`. Real: "Conversion to Aur failed" at the Hotfolder, no `Split` in the Journal, job `<Name>` = the batch's XML name (`30-09-2026_PRINTED_090007-...`). **Before 2026-10-14 this case was read as ONE row with that name as `file_id`** - it matched no file, so no badge and no "Resolved" button, only the Overview counter (30-07, 04-08, 30-09 on the live DB).
  - **NONE** (pre-split, e.g. "File not found or not accesible") → also `scope: BATCH`, one row per document.
  - BATCH rows are named from `RipFlowJob.Documents` (RipFlow's own list, so the names are exactly the file stems), from the job-level list only when that one is missing.
- **Real-structure notes (don't re-derive wrongly):** the true Job root is `parsed.Job`; `RipFlowJob` is at `Job.ProcessNodes.XML.RipFlowJob` (**NOT** a direct child of `Job`). `documentId` (XWD) is taken from the filename stem (regex `/XWD[0-9a-f]+/i`), **NOT** from `UserData.DocumentId` (absent/inconsistent across PF exports); it's a nullable backup key. `RipFlowJob.BatchId` (= `rip_errors.batch_id`) is written by RipFlow itself (`createXML.js`): `dd-mm-yyyy/PRINTED_...` = the last two segments of `batch_path`.
- **KNOWN LIMIT:** verified on real exports of Layout-fail (one document), Conversion-to-Aur at the Hotfolder (all documents), File-not-found and OK. Other failing nodes (Nester, Resize, StepRepeat) are NOT yet seen live. An unknown shape listing several documents lands on the BATCH side - visible on every file and the header, never lost the way the batch failures were before. Pinned by `parseRipErrorXml.test.js` (fixtures follow the real element structure, names replaced).

**Ingest + poll** — `ripErrorHandlers.js` `scanRipErrors()` reads `{storagePath}\<folders.ripError>` (sibling of `PRINTED/`, never hardcoded). **No usable name** (profile unreadable, key missing, not one plain folder name) → nothing is read and the answer is the ENOENT one below, `{success:true, data:getOpenRipErrors()}`, with one `console.warn` per hour (`createLogOnce` - the poll runs every 30 s); there is NO fallback to Alex's name (rule 24). Pinned by `ripErrorHandlers.scan.test.js`. It filters `*.xml` only (ignores the `.tif`), `parseRipErrorXml` + `insertRipError` per row (INSERT OR IGNORE dedup on `(job_guid, file_id)`). **One xml = one job:** before inserting, `ripErrorJobHasOtherFiles(jobGuid, fileIds)` asks whether the DB already holds that job under OTHER files - read before, the other way - and if so the xml is skipped. Without it the parser change of 2026-10-14 would have re-opened the resolved 30-09 failure as 14 new rows (its xml is still in the folder; the old row's `file_id` was the batch name). Rows for the SAME files are not "other", so a job cut short by a failed write (`runWrite` → `false` on SQLITE_BUSY) is completed by the next scan; a failed read answers `true` (skip this round, ask again in 30 s). Pinned by `ripErrorHandlers.job.test.js`. Per-file try/catch (one bad xml can't sink the scan), missing folder (ENOENT) → nothing ingested, still `{success:true, data:getOpenRipErrors()}` (the open rows already in the DB — NOT `[]`, so a folder deleted mid-session does not wipe the badges); any other `readdir` error → `{success:false}`; otherwise returns `getOpenRipErrors()`. IPC `rip-errors:scan` / `rip-errors:get` → `window.api.ripErrors` → `ripErrorService`. **Global 30s poll in `App.jsx`** (`loadRipErrors`) runs the whole session regardless of `activeView`, so badges stay fresh in both views — but only while `isFeatureEnabled("ripErrors", shopProfile)` is true: it lives in its own effect keyed on that flag, NOT in the startup sequence (there the profile has not resolved yet, and the fail-closed flag would skip the scan for the whole session). The same effect is keyed on `store.pollingPaused` (ETAP 4 4-power): no scan while the station sleeps or is locked, one at once when the pause ends.

**Store** — `ripErrors {}` keyed `fileId → row`, open-only, most-recent-wins (one file may hold multiple open DB rows; the store/badge surface the latest). Actions: `loadRipErrors()`, `removeRipError(fileId)` / `clearRipErrorsForFiles(ids)` (optimistic clear on rollback), `resolveRipError(fileId)` and `resolveRipErrorJob(jobGuid)` (manual resolve of a file / of a whole-batch failure — DB write first, store clear only on success; the job one drops every file of the job via `withoutRipErrorJob`). Pure helpers in `utils/ripErrorsByFile.js`: `latestRipErrorPerFile`, `batchRipErrorOf(fileIds, ripErrors)` (the most recent `scope: BATCH` row among a batch's files, or `null`), `countRipErrorEvents` (failures, not files: a BATCH row counts once per `job_guid`, a file / scope-less row once per file), `withoutRipErrorJob`.

**UI — badges** — red **"RIP Error"** badge (`LuTriangleAlert`) per file in BOTH `ProductionCard` and BatchHistory `FileRow`, shown when `store.ripErrors[stem]` exists (stem = `file.name.replace(/\.[^.]+$/,"")`). Both rows stay presentational — `Production.jsx` and `BatchRow.jsx` (already store subscribers) read `ripErrors` and pass the `ripError` prop down (mirrors how reprint/stageRow reach the rows). `BatchRow` also shows a **batch-header count badge** `"N RIP Error(s)"` (non-interactive) = this batch's files ∩ `ripErrors` with the same stem derivation → header count == expanded file-badge count by construction. Red palette `#FEF2F2` / `rgba(220,38,38,.4)` / `#DC2626`.

**UI — whole-batch failure (scope BATCH, FILIP 2026-10-14: "header + files").** Every file of the batch carries its normal badge (its own row), AND the batch header shows a **clickable** `"RIP Error · whole batch"` badge - `BatchRow` (in place of the count badge, which would only repeat that every file has one) and Production's `BatchGroupHeader` (new `onRipBadgeClick` prop, same `setRipPopover` as the cards). Both find it through `batchRipErrorOf` over the batch's file stems, so no batch-name matching. The Overview "RIP errors" pill counts through `countRipErrorEvents`: one batch failure = 1, however many files it badges.

**UI — popover (`RipErrorPopover/`)** — clicking the per-**file** badge opens one shared anchored popover (state owned by each view, portaled to `document.body` at the call site like `ContextMenu`). Positioning (anchor edge-flip clamp) + backdrop close (`onPointerDown → onClose`) are **lifted from `ContextMenu` (not imported)**; z-index 2999/3000. Shows Error message / failed node / time (local `formatRipTime`, `HH:MM DD/MM/YYYY` — no shared date helper exists) / file_id, plus a **Copy** button → `navigator.clipboard.writeText` (pattern mirrors `SessionLogs.jsx`) writing the 5-line block (`RIP Error` / `File:` / `Error:` / `Node:` / `Time:`), label `Copy → Copied! → revert ~1.5s` (timeout cleared on unmount). Badge `onClick` + popover interior `stopPropagation` so a click never expands the BatchHistory row or toggles the ProductionCard selection. The **batch-header count badge is NOT clickable**.

**Resolve lifecycle — TWO paths.** (1) **Rollback (automatic):** `rollbackFile` → `resolveRipErrorsByFile(stem)` using the SAME stem key as `clearFileStage`; `rollbackBatch` loops it over `pdfNames` stems (**not** `batch_path` — `rip_errors.batch_id` is the XML BatchId string, so per-stem is the correct key). Runs only on rollback **success**. The store optimistically drops the stem(s) at every rollback-success site (Production `handleRollbackDecisions`; BatchHistory bulk/single/batch handlers — batch uses `dayGroupsRef.current` for the batch's file stems) so badges + header count clear instantly; the 30s poll reconciles against the DB (resolved rows excluded by `getOpenRipErrors`). (2) **Manual (deliberate, from the UI):** a **"Resolved"** button in `RipErrorPopover` next to Copy — for an error the operator has dealt with WITHOUT returning the file to the inbox (job re-sent, RIP queue cleared). Path: `RipErrorPopover` → `store.resolveRipError(fileId)` → `ripErrorService.resolveRipError` → IPC `rip-errors:resolve` → the SAME `resolveRipErrorsByFile`. Both paths resolve **ALL** open rows for that `file_id`. **A whole-batch failure (scope BATCH) is resolved as ONE event**: the popover - opened from the header or from any file of the batch - shows "RIP Error — whole batch" with the `batch_id` instead of the file, copies `RIP Error (whole batch)` / `Batch:` / ..., and "Resolved" goes `store.resolveRipErrorJob(job_guid)` → IPC `rip-errors:resolveJob` → `resolveRipErrorsByJob` (every open row of the job). Both IPC resolves share `resolveOpenRows` in `ripErrorHandlers.js` (same validation + runWrite-boolean contract; `INVALID_FILE_ID` / `INVALID_JOB_GUID`). A rollback still resolves per file, so rolling back ONE file of a failed batch clears only that file; the header badge stays while any file of the batch still carries the row.

**`rip-errors:resolve` reads the `runWrite` return value, NOT a try/catch.** `resolveRipErrorsByFile` never throws — it returns `false` when the DB is unavailable or the write fails. The handler derives `success` **from that boolean** (`false` → `toIpcError` with `DB_WRITE_FAILED`); relying on the absence of an exception would report `success:true` against a dead DB and the store would drop the badge of an error still open in the DB. The store calls `removeRipError(fileId)` **only** on `success` — a failed write leaves the badge in place and the popover open for a retry. The store does NOT notify; the toasts (Success / Error) belong to the popover.

**`RipErrorPopover` receives the row, not a `fileId`.** `error.file_id` is already the stem; the displayed `fileId` carries a `"—"` fallback, so the backend key is `rawFileId` (non-empty string or `null`) — the button is `disabled` when it is `null`.

**PrintFactory side (operational context):** a single Export node wired to every workflow port writes the per-failed-job `<name>.tif` + `<name>.xml` into `AUTOMATION_WORKFLOW_ERROR/`. The Export uses `Content=Layout` + Export XML (Document/Original was abandoned — it couldn't access the `PRINTED/` pdf). RipFlow reads only the `*.xml`. **TIFF cleanup is out of scope for RipFlow** — a separate scheduled task should prune old TIFFs; RipFlow never deletes from the shared share.
